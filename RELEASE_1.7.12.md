# Причал Core 1.7.12 — оптимизация и фото из Mini App

## Что изменилось

- Контроль проверок: групповые счётчики вместо запросов по каждому магазину.
- Задачи: пакетная загрузка целей, исполнителей и чек-листов; страницы по 50 записей с переходами.
- Профиль: пакетная загрузка задач, тестов, попыток и ознакомлений; ограничение размера истории до SQL.
- Пересменки: пакетные данные отчётов и фотографии полей, повторное использование данных в проверках и отображении.
- Проверки: пакетная загрузка фотографий и форм; фильтры истории применяются до ограничения страницы.
- База знаний: облегчённые списки без всех медиа; пакетные авторы, разделы и отметки ознакомления. Ошибки проверки прав больше не открывают доступ к опубликованной статье.
- Диагностика: X-SQL-Count, X-SQL-Time-ms, X-DB-Acquire-ms и существующий X-Process-Time-ms. DB-Acquire включает ожидание пула, создание соединения и pre-ping, а не только ожидание.
- Пул БД настраивается через DB_POOL_SIZE, DB_MAX_OVERFLOW, DB_POOL_RECYCLE, DB_POOL_TIMEOUT. По умолчанию сохранены 5/10/300/30. Проверка TLS и pre-ping сохранены.
- Версионированный запуск схемы: миграции и старые backfill не повторяются при каждом рестарте. На PostgreSQL миграции сериализованы advisory lock.
- Telegram webhook сохраняет событие в БД и отвечает после сохранения. Обработка и отправка уведомлений происходят вне HTTP-запроса. Фото и сообщения обрабатываются отдельными потоками.
- Планировщик группирует получателей и счётчики, выполняет правила раз в минуту, журналирует ошибки. Бизнес-правила по времени сохранены.

## Новые фотографии

Камера или галерея → превью → сжатие → прямая загрузка в приватный S3 → серверная проверка → привязка к записи. Прогресс и повтор доступны в диалоге. Фото больше не требуют перехода в Telegram-чат.

Поддержаны аватар, поля пересменок, проверки и их пункты, результаты задач и пункты чек-листа, медиа статей, изображения вопросов тестов. В диалоге можно удалить прикреплённое фото, если состояние записи и права это разрешают. Для мелкого текста есть режим повышенного качества.

Новые фотографии получают UUID и не требуют Telegram file_id. Добавлены оригинал, миниатюра, журнал привязок и устойчивая сессия загрузки. Существующие фотографии остаются в S3: миграция связывает их с новой моделью через уже имеющиеся mappings. Превью старых S3-фото создаются постепенно в фоне.

Повторное завершение загрузки возвращает прежний результат. Сервер проверяет реальное изображение, объём, владельца, права и состояние записи непосредственно перед прикреплением. Повторный PUT по ещё действующей временной ссылке не изменяет принятое фото: окончательные ключи доступны для записи только серверу. Фоновые задания возобновляются после рестарта.

Галереи используют миниатюры, отложенную загрузку и максимум три параллельных скачивания. Кеш ограничен по числу и объёму объектов, очищается при смене сессии; запросы удалённых с экрана изображений отменяются. Доступ к фото остаётся через авторизованный сервер Core.

Фотографии, перенесённые из проверки в задачу, используют один media asset. Удаление исходной привязки не удаляет доказательство из задачи. Принятые отчёты и уже использованные в попытках вопросы не допускают замены фото.

Видео и обычные документы продолжают использовать существующий сценарий Telegram; изменение касается фотографий.

## Развёртывание на Bothost

1. Сделайте резервную копию PostgreSQL перед обновлением схемы.
2. Загрузите этот архив: Dockerfile и main.py находятся в корне.
3. Сохраните прежние DATABASE_URL, DATABASE_SSLMODE, PHOTO_STORAGE=s3 и все S3-переменные. Встроенный CA Timeweb сохранён.
4. APP_URL должен содержать адрес Mini App, например https://prichalcore.bothost.tech. Если APP_URL пуст, приложение использует DOMAIN, как и раньше.
5. Запустите приложение. Схема расширяется автоматически; уже существующие файлы не переносятся и не удаляются. JS/CSS получили новые имена 1.7.12.

Приложение по умолчанию добавляет собственное CORS-правило для PUT с origin из APP_URL, сохраняя правила остальных проектов общего бакета. Ключ S3 должен иметь право читать и изменять CORS. Если это право отсутствует, приложение запустится, но браузерная загрузка фото потребует правила в панели Timeweb:

- Allowed Origins: https://prichalcore.bothost.tech (или фактический origin APP_URL)
- Allowed Methods: PUT
- Allowed Headers: content-type
- Expose Headers: ETag
- Max Age Seconds: 600

Не заменяйте правила других проектов. После выдачи прав можно выполнить `python scripts/configure_media_cors.py`; скрипт также сохраняет чужие правила. Автонастройку можно отключить MEDIA_AUTO_CORS=false, если правило уже управляется вручную. Отдельная запись/чтение тестового файла не выполняется.

Ограничение готового загружаемого файла по умолчанию 12 МиБ (MEDIA_MAX_BYTES). Это лимит проверки и обработки Core, а не жёсткая квота приёма произвольных байтов S3 по подписанной PUT-ссылке. Клиент сам уменьшает фото; просроченные временные объекты убираются только из префикса Core.

Изменение схемы расширяющее: старые Telegram-поля сохранены. После появления новых фото откат только к старому коду не покажет эти фото, поскольку старый код не знает media_id. Для отката используйте согласованную копию БД и предыдущий выпуск; новые S3-объекты не удаляйте.

## Результаты локальной проверки

На одинаковых данных: администратор, 25 магазинов, 50 задач. Количество SQL за один авторизованный запрос, с учётом авторизации:

| Экран | 1.7.11.8 | 1.7.12 |
|---|---:|---:|
| Контроль проверок | 77 | 4 |
| Мои задачи | 103 | 7 |
| Работа в профиле | 57 | 8 |

Это замеры числа SQL на SQLite, не времени работы Timeweb. Оригинальная сборка для сравнения побайтно сверена с исходным архивом. Проверочный скрипт: `python scripts/benchmark_sql.py /путь/к/исходникам`.

Прошли 21 проверка pytest: все семь назначений фото (проверка и её поле отдельно), запрет доступа к чужому профилю/чужому результату задачи, размер и повреждение файла, истечение сессии, повторное подтверждение, смена статуса отчёта, отзыв доступа, восстановление обработки, миграция имеющихся связей, повтор миграции, общее фото проверки и задачи, очистка временных объектов без затрагивания другого проекта, сохранение CORS-правил, очередь уведомлений, история с фильтром до LIMIT и стабильность числа SQL. Подпись PUT проверена реальным boto3 с тестовыми локальными реквизитами без сетевого запроса.

Также прошли существующие performance_smoke_test.py (главная — 19 SQL), security_smoke_test.py, разбор Python и проверка синтаксиса JavaScript. В DOM-проверке интерфейса пройден сценарий выбор файла → отправка → подтверждение → закрытие диалога, без запроса Telegram-фотографии. Декодирование/сжатие браузером и сам PUT в этой DOM-проверке заменялись заглушками.

Не выполнены здесь: запуск миграции на реальном PostgreSQL, реальная загрузка/скачивание Timeweb S3 и визуальная проверка Telegram WebView. Доступа к рабочим сервисам не использовалось. Установка Chromium для визуальной проверки не удалась из-за недоступного корректного пакета браузера. Поэтому работоспособность на конкретном сервере и совместимость камеры устройства подтверждаются после одного общего развёртывания.

Очереди Telegram обеспечивают повторную обработку после сбоя; Telegram API не даёт общей гарантии exactly-once. При аварии между внешней отправкой и фиксацией результата возможно повторное сообщение. Входящие update_id дедуплицируются; фото и их привязки имеют собственную идемпотентность.

## Команды локальной проверки

`pip install -r requirements.txt pytest`

`pytest -q tests/test_upgrade.py`

`python scripts/performance_smoke_test.py`

`python scripts/security_smoke_test.py`

Рабочий PostgreSQL и бакет этими тестами не используются. Установка дополнительных систем, Redis, Celery или отдельного Node-сервера не требуется.
