# Причал Core v0.1 — чистая сборка

Новый Telegram-бот + MiniApp, созданный с нуля и не зависящий от старого бота «Заявки».

## Архитектура

```text
Telegram Bot / MiniApp
        ↓
FastAPI (Python, Bothost)
        ↓
Neon PostgreSQL
        ↓
AI Agent / Saby analytics (позже через API)

Фотографии физически остаются в Telegram.
В Neon хранятся file_id, связи и метаданные.
```

## Что уже заложено

- Telegram MiniApp с проверкой `initData` (HMAC).
- Серверные сессии и роли.
- Роли: продавец, наставник, управляющий, операционный директор, руководитель, администратор.
- Привязка сотрудников к одной/нескольким точкам.
- Админ-раздел: пользователи, точки, поставщики, товары.
- Товары по поставщикам и возможность ограничивать ассортимент по точкам.
- График/дедлайн поставщика для конкретной точки.
- Заявки поставщикам.
- Пересменки: утро/вечер.
- Проверки магазинов по чек-листу.
- Задачи и сроки.
- Инкассации.
- Инциденты («красный / жёлтый / зелёный»).
- Запросы на подмену (API; UI будет расширяться).
- Фото через Telegram: MiniApp создаёт запрос → сотрудник отправляет фото в чат боту → Core сохраняет `file_id` в Neon.
- Метрики план/факт для последующей загрузки из Saby/AI-контура.
- Контракт для подключения отдельного AI-агента.
- Таблицы-задел: тайный гость, наставничество/обучение, фокусная задача месяца, недельный отчёт управляющего, audit log.
- Опциональный scheduler: контроль несданных пересменок в 08:10 и 20:10.

## 1. Загрузка в GitHub

Для чистого старта замените содержимое репозитория `prichalcore` содержимым этого архива.

В корне обязательно должны лежать:

```text
main.py
requirements.txt
README.md
app/
miniapp/
```

**Dockerfile в этой сборке намеренно отсутствует.** На Bothost используем штатный Python-деплой, максимально близкий к схеме вашего рабочего бота.

## 2. Настройки Bothost

Создание/редактирование бота:

- Платформа: **Telegram**
- Язык: **Python**
- Git: `https://github.com/fridgeby-droid/prichalcore.git`
- Ветка: `main`
- Главный файл: `main.py`
- Использовать домен: **Да**
- Домен: `prichalcore.bothost.tech`
- Внутренний порт: **5000**
- Custom Dockerfile: **Выключен**

`main.py` слушает `0.0.0.0` и `PORT`, fallback — `5000`.

## 3. Переменные окружения Bothost

Обязательные:

```text
BOT_TOKEN=<токен нового Telegram-бота>
APP_URL=https://prichalcore.bothost.tech
PORT=5000
DATABASE_URL=<pooled connection string Neon>
DATABASE_URL_DIRECT=<direct connection string Neon>
TELEGRAM_WEBHOOK_SECRET=<случайная строка 32–64 символа>
BOOTSTRAP_ADMIN_TELEGRAM_ID=<ваш Telegram ID>
APP_TIMEZONE=Asia/Yekaterinburg
APP_ENV=production
LOG_LEVEL=INFO
AUTO_SET_WEBHOOK=true
SESSION_TTL_HOURS=24
TELEGRAM_AUTH_MAX_AGE_SECONDS=86400
INTERNAL_API_SECRET=<ещё одна случайная длинная строка>
```

На первом запуске:

```text
ENABLE_SCHEDULER=false
```

Когда добавлены точки, управляющие и продавцы, можно переключить на:

```text
ENABLE_SCHEDULER=true
```

Пока AI-агент не подключён:

```text
AI_AGENT_URL=
AI_AGENT_SECRET=
```

### Как узнать BOOTSTRAP_ADMIN_TELEGRAM_ID

После первого запуска отправьте боту:

```text
/whoami
```

Он пришлёт ваш Telegram ID. Внесите его в Bothost как `BOOTSTRAP_ADMIN_TELEGRAM_ID` и выполните новый deploy.

## 4. Neon

Используются две строки:

- `DATABASE_URL` — **pooled** endpoint (`-pooler` в hostname). Для обычной работы приложения.
- `DATABASE_URL_DIRECT` — **direct** endpoint. Для DDL/создания схемы.

Схема v0.1 создаётся автоматически при первом старте через SQLAlchemy `create_all` на direct connection.

Это сознательный выбор для раннего этапа, когда структура будет активно меняться. Перед стабильным production-релизом переведём изменения схемы на Alembic migrations.

## 5. Проверки после deploy

Откройте:

```text

```

Ожидается:

```json

```

Затем:

```text

```

Ожидается:

```json

```

После этого `/start` в Telegram. Webhook ставится автоматически при старте приложения.

## 6. Первый запуск MiniApp

1. Администратор открывает MiniApp первым (его ID должен совпадать с `BOOTSTRAP_ADMIN_TELEGRAM_ID`).
2. В `Ещё → Администрирование` добавляет магазины.
3. Добавляет поставщиков.
4. Добавляет товары.
5. Остальные сотрудники нажимают `/start` и открывают MiniApp.
6. Они попадают в статус `pending`.
7. Администратор назначает роль и магазин(ы).
8. Сотрудник заново открывает MiniApp и получает свой интерфейс.

## 7. Фото в Telegram

Пример пересменки:

1. Продавец сдаёт пересменку в MiniApp.
2. Нажимает добавить фото.
3. Core создаёт `pending_photo_upload` и отправляет продавцу сообщение в Telegram.
4. Продавец отправляет фото обычным сообщением боту.
5. Webhook получает Telegram `file_id` / `file_unique_id`.
6. В Neon сохраняется связь фото с пересменкой/проверкой/задачей.
7. Сам файл остаётся на серверах Telegram.

Backend умеет отдавать фото авторизованному пользователю через защищённый proxy endpoint, не раскрывая `BOT_TOKEN` браузеру.

## 8. Связь с AI-агентом

В Core предусмотрены:

```text
POST /api/integrations/store-metrics
```

для загрузки агрегированных данных Saby/аналитического контура, и:

```text
POST /api/ai/store/{store_id}
```

для обращения к отдельному AI-сервису.

Когда AI-агент будет готов, задаём:

```text
AI_AGENT_URL=https://...
AI_AGENT_SECRET=...
```

Core не будет хранить бизнес-логику AI в MiniApp — AI остаётся отдельным «мозгом», а Core становится общей операционной системой и источником структурированных данных.

## 9. Рабочие правила, заложенные в архитектуру

- управляющий видит только закреплённые точки;
- глобальные роли видят сеть;
- магазины/поставщики/товары не удаляются из истории — их можно отключать (`is_active=false`);
- пересменки — утро и вечер;
- целевой контроль точки — 3 раза в неделю;
- инкассация — 2 раза в неделю на точку;
- задачи имеют ответственного, статус и срок;
- проблема может иметь красный/жёлтый/зелёный приоритет;
- план/факт и AI-аналитика подключаются через единые `store_id`;
- фото хранятся отдельно от PostgreSQL;
- воскресенье/режим доступности 07:30–22:30 пока являются организационными правилами, а не жёсткой блокировкой функций в коде.

## 10. Что будем править следующими итерациями

Это v0.1 — фундамент и рабочий MVP. Следующими итерациями целесообразно сделать:

2. полноценное редактирование справочников, а не только добавление;
3. сложную логику заявки (дни поставки, дедлайны 08:00/10:00, фильтры управляющего);
4. обязательный комплект фото пересменки;
5. конструктор чек-листа проверки;
6. автоматическое создание задачи из нарушения;
7. контроль `3/3` проверок и `2/2` инкассаций по каждой точке;
8. модуль подмен с рассылкой свободным сотрудникам;
9. недельный отчёт управляющего;
10. тайный гость и рейтинг магазинов;
11. наставники/стажёры/обучение;
12. фокусная задача месяца;
13. Saby/AI интеграция;
14. Alembic migrations + staging branch Neon перед production.
