# Причал Core v1.7.21

Основа: v1.7.20. Изменения окружения, миграции базы и перенос серверов не нужны.

## Оптимизация администрации

- `/api/admin-center/users`: привязки магазинов загружаются одним запросом для всего списка. В тестах для 2 и 52 пользователей — по 4 SQL-запроса вместе с авторизацией. В присланном серверном логе предыдущей версии было 47 запросов и 2583,8 мс; время новой версии на сервере пока не измерялось.
- `/api/admin-center/audit`: авторы загружаются вместе с записями журнала. В тестах для пустого журнала и 50 записей — по 2 SQL-запроса с авторизацией.
- `/api/admin-center/system`: все настройки загружаются одним запросом, всего 2 с авторизацией.
- Детали роли считают пользователей через COUNT, не загружая полные записи пользователей.
- Формат ответов, статусы pending, назначения ролей, привязки магазинов и проверка администратора сохранены.

## Диагностика Bothost → Timeweb

Адрес прежний: `/db-health`. Основные поля сохранены; добавлены:

- `query_warm_avg_ms`: среднее время запросов №2–10 через одно уже открытое соединение.
- `query_warm_median_ms`: медиана тех же девяти запросов.
- `metadata_ms`: получение имени базы.
- `transaction_finish_ms`: завершение диагностической транзакции через rollback.
- `pool_return_ms`: закрытие обёртки соединения/возврат в пул после rollback.

`checkout_ms` по-прежнему включает получение соединения из пула, проверку его работоспособности и, при необходимости, открытие нового соединения. Он не является отдельным замером чистого сетевого ping или TCP/TLS.
`query_first_ms` может включать начало транзакции. Повторные SELECT 1 помогают отделить эту составляющую от стоимости очередного обращения к базе.
`release_ms` включает завершение транзакции и возврат соединения в пул.

Если повторные SELECT 1 стабильно занимают около 50 мс, значительна стоимость каждого обмена с PostgreSQL. Она включает сеть, обработку и ожидание на сервере/драйвере — это не доказательство исключительно сетевой проблемы. Если высок только checkout, нужно отдельно исследовать пул, проверку соединения или создание подключения. Если высок первый SELECT, а повторные быстрые, исследовать начало транзакции/первое обращение.

## Что сделать после установки

1. Обновить исходники на Bothost и перезапустить приложение штатным способом.
2. Проверить `/health`: версия `1.7.21`. Полностью закрыть и открыть MiniApp.
3. Открыть «Админ → Пользователи». Проверить список и прислать новую строку Slow API, если она появилась.
4. Открыть `https://prichalcore.bothost.tech/db-health` и сохранить JSON-ответ. Повторить 2–3 раза и передать результаты для сравнения. Адрес и пароль подключения передавать не нужно.
5. По замерам решить, остаётся ли инфраструктурная задержка. Перенос приложения или базы этой сборкой не выполняется.

## Проверено

10 локальных серверных тестов прошли: постоянное число SQL-запросов, формат данных пользователей/магазинов, запрет доступа обычной роли, поля диагностики, существующие сценарии одобрения pending-пользователя и назначения доступа. Синтаксис Python проверен.

Тестовая база — SQLite. Соединение с рабочей базой Timeweb и серверная установка не проверялись. Значения latency с рабочего сервера необходимо получить после обновления. Изменений поведения интерфейса в этой версии нет; обновлены имена статических файлов для версии сборки.
